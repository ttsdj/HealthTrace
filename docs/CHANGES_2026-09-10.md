## 1. JWT 签名密钥不再回退到公开常量（fail-closed）

**修复前**：`backend/infra/auth.py` 中

```python
SECRET_KEY = os.getenv("JWT_SECRET_KEY", "change-this-secret")
ALGORITHM = os.getenv("JWT_ALGORITHM", "HS256")
```

两处问题：

1. 未配置 `JWT_SECRET_KEY` 时使用硬编码的 `"change-this-secret"` 签名。
   该常量就在仓库里，任何人都能离线伪造任意用户（含 `admin`）的令牌。
2. `JWT_ALGORITHM` 可被环境变量覆盖。若被设为 `none`，
   `python-jose` 会接受无签名令牌——一条配置错误即可变成认证绕过。

**修复后**：

- 算法在代码中固定为 `HS256`，不再读取环境变量。
- 新增 `jwt_secret_key()`：每次调用实时解析密钥，缺失、长度不足 32 字符、
  或命中占位符特征（`replace` / `your-` / `change-this` / `example` / `placeholder`）
  时抛 `JWTConfigurationError`，**绝不回退**。
- 签发与校验路径统一把该异常转成 `503 authentication is not configured`；
  错误详情不回显具体原因，避免未认证调用者探测密钥配置状态。
- `STRICT_STARTUP=true`（`docker-compose.app.yml` 默认打开）时启动即校验，配置错误直接拒绝启动。
- `scripts/production_preflight.py` 复用同一份判定逻辑，不再各写一份。

**测试**：`test_signing_key_*`、`test_create_access_token_refuses_to_sign_without_a_key`、
`test_login_is_unavailable_when_the_signing_key_is_missing`、`test_signing_algorithm_is_pinned_to_hs256`。

**附带改动**：新增 `tests/conftest.py`，用 autouse fixture 为测试进程注入一把合法测试密钥。
否则 CI 在 `cp .env.example .env` 之前跑 pytest 会全部失败。

## 2. Milvus filter 表达式转义（堵住"单请求删库"）

**修复前**：`backend/api/resources.py`

```python
delete_expr = f'filename == "{filename}"'
```

Milvus filter 是**解析执行**而非参数化绑定。文件名由请求控制，
构造 `x" or filename != "` 即可闭合字符串字面量并追加条件，
得到的表达式等价于"匹配集合内所有行"——一次删除请求清空整个集合
（该删除路径同时清理 PostgreSQL 父分块与 Redis 缓存）。
同类插值还出现在 `patient_documents.py`、`patient/retrieval.py`、`rag/utils.py`、
`incremental_update.py`、`milvus_client.get_chunks_by_ids()`。

**修复后**：新增唯一实现 `backend.indexing.milvus_client.escape_filter_value()`，
先转义反斜杠再转义双引号；上述全部调用点改为经过它。
`incremental_update.py` 原有的 `_escape_filter_value` 改为转发，避免两份实现漂移。

**测试**：`test_public_document_delete_escapes_the_filename` 用桩 Milvus 捕获真实下发表达式，
断言注入串仍留在字面量内部（未转义引号恰好只有两个定界符）、且只有一个子句。

## 3. `clinician` 临床审核凭证不再可自助获取

**修复前**的完整提权链（已端到端复现）：

1. `POST /auth/register` 自助注册，`resolve_role()` 把非 admin 请求一律降为 `user`；
2. 调用任意患者域接口，`backend.patient.scope.ensure_user_scope()` 自动创建个人租户，
   并把该用户设为 `TenantMembership(role="owner")`；
3. `POST /tenant/members {"username": <自己>, "role": "clinician"}` ——
   `_tenant_admin_membership()` 只校验"是本租户 owner/admin"，通过；
   `TenantMemberCreate.role` 的允许集合是 `admin|clinician|viewer`；
4. 于是该用户获得 `TenantMembership(role="clinician", status="active")`；
5. `backend.evaluation.golden_review.reviewer_role()` 接受该成员身份作为临床审核角色，
   且**不限定租户**、对所有数据集生效；
6. `golden_readiness()["clinical_claim_allowed"]` 随之为真 ——
   任何人可为自己签发临床审核意见，golden 门禁形同虚设。

**修复后**：`clinician` 被认定为**平台级凭证而非租户内部职位**
（它是 `clinical_claim_allowed` 的来源），因此
`POST /tenant/members` 中分配 `clinician` **要求调用者为全局管理员**
（`backend/api/routes/access_control.py` 的 `_OPERATOR_ONLY_MEMBER_ROLES`）。

选择"限制分配方"而非"要求 `User.role == 'clinician'`"的原因：
后者与 `docs/SECURITY_AND_ACCESS.md` 记录的 `TenantMembership(owner/admin/clinician/member)`
模型冲突，且 `resolve_role()` 不会把任何请求映射为 `clinician`，
改后该凭证将无任何合法获取途径。

**测试**：`test_tenant_admin_cannot_mint_the_clinician_credential`
（修复前断言 `403` 实得 `200`，已实测确认）、
`test_platform_administrator_can_still_assign_the_clinician_role`（确认合法路径未被误伤）。

**连带调整**：`tests/test_access_security.py` 中原本用 `role="clinician"` 走通的成员流程
改为 `role="viewer"`——该用例验证的是"成员身份 + 患者授权"边界，与角色值无关。

## 4. 滥用防护：指标标签基数、凭证接口限流、审计洪泛

前两项在审计中已用探针确认可被**未认证**请求触发，是本轮唯一能被做成 DoS 的问题。

### 4.1 指标标签基数有界

**修复前**：`backend/security/middleware.py` 在 `finally` 中

```python
route = getattr(request.scope.get("route"), "path", None) or path
```

路由未匹配时（扫描器随机 URL）回退到**原始请求路径**，并作为
`healthtrace_http_requests_total{route=...}` 的标签值写入
`backend/observability/metrics.py` 的模块级 dict。
每个不同的 URL 产生一条新时间序列，dict 无上限增长直到进程 OOM。

**修复后**：未匹配路由统一归入单一序列 `UNMATCHED_ROUTE = "/unmatched"`
（这类请求仍被计数，扫描行为依旧可见）。
`metrics.py` 另加第二道防线：不同路由模板数量超过
`HEALTHTRACE_METRICS_MAX_ROUTES`（默认 200）后折叠为 `/other`，
非 `/` 开头的标签值也归入 `/unmatched`。
新增 `reset_process_metrics()` 供测试清理模块级状态。

### 4.2 `/auth/login` 与 `/auth/register` 限流

**修复前**：两个接口没有任何速率限制。注册尤其廉价可滥用——一次请求会创建
`User` + `Tenant` + `PatientProfile` 以及两条授权记录。

**修复后**：新增 `backend/security/rate_limit.py`，进程内固定窗口计数器，
经 FastAPI 路由级依赖挂载。默认登录 20 次/60 秒、注册 5 次/300 秒，
可由 `HEALTHTRACE_LOGIN_RATE_LIMIT` 等变量调整。超限返回 429 + `Retry-After`。

**两个必须知道的部署约束**（写在模块 docstring 里，也在 `.env.example` 注释中）：

1. 计数器在**单个 worker 进程内**。N 个 uvicorn worker 的实际上限是配置值的 N 倍。
2. 客户端身份默认取对端地址。**反向代理后面所有用户共用一个地址、共用一个桶**，
   此时需要把 `HEALTHTRACE_TRUST_PROXY_HEADERS` 打开；但只有在代理由你控制并会
   覆写该头时才能打开，否则任何人都能伪造 `X-Forwarded-For` 换桶绕过限流。

因此本进程内限流**不能替代反向代理层的限流**，它只是让暴力破解和洪泛付出成本。

计数器本身也有界：表满时先清理过期窗口，仍满则**拒绝**（fail-closed），
不会成为新的无限增长点。

### 4.3 未匹配路由不再写入审计行

**修复前**：只要路径以 `/patient`、`/auth` 等前缀开头，中间件就会写一条审计记录——
包括**没有匹配到任何路由**的 404。未认证请求遍历随机 URL 即可持续往审计表插行
（`actor_user_id` 为空的 404 记录）。

**修复后**：仅当请求真正匹配到路由时才写审计（`matched_route is not None`）。
判据是"有没有发生访问决策"：未匹配路径没有触达任何端点、没有读写任何资源、
没有做任何授权判断，因此没有可问责的内容；这类请求仍被计入指标。

**没有**采用"按 IP 限流后丢弃审计"的方案：那会让攻击者通过洪泛压制
同一出口 IP 下其他用户的审计记录，对医疗系统而言是审计完整性倒退。
已匹配路由上的 401/403/404（真实授权拒绝）**照常审计**，并由回归测试锁定。

## 5. 漏斗检索的候选文档查询越过了租户边界

**修复前**：`backend/rag/funnel.py` 的 `_candidate_document_ids()` 只用主题词构造谓词：

```python
clauses = " or ".join(f'section_path like "%{t}%"' for t in terms)
filter_expr = f"chunk_level in [1, 2] and ({clauses})"
```

`stage_document()` 的患者分支把该谓词直接发给**患者记录集合**
（`healthtrace_patient_record_text_v1`，全平台共用），**没有 tenant_id / patient_id 条件**。
该集合里每个租户的患者文档都在，所以这次查询匹配的是**所有患者**的文档，
而返回的 `document_id` 会一路回传到客户端：

1. `_candidate_document_ids()` 的结果写入 `trace["document_ids"]`（`funnel.py:318`）；
2. `run_funnel()` 把它放进 `funnel_trace["document"]`（`funnel.py:433`）；
3. `retrieve_initial()` 把整个 `funnel_trace` 放进 `rag_trace`（`pipeline.py:258`）；
4. `/chat/stream` 的 trace 事件用 `json.dumps({'type': 'trace', 'rag_trace': rag_trace})`
   **原样**下发（`chat/service.py:593`），不经过 `RagTrace` 响应模型——
   被该模型丢弃的 `funnel_trace` 在这里照样发给客户端。

于是一个已登录用户只要提一个患者域问题，就能在响应里读到**其他租户**的患者文档标识。
（1–3 为读代码确认，4 为原样 `json.dumps` 确认；回归测试锁定的是根因，即下发的过滤表达式。）

两点补充：

- 患者文档 id 形如 `doc-{uuid4()}`（`patient_documents.py:389`），不含患者姓名，
  因此泄露的是跨租户的不透明标识符，以及"平台上命中这些词的文档数量"这一计数，
  不是病历正文——正文由 `retrieve_patient_records()` 自身的 scope 过滤保护。
- 同一处缺陷也是**功能缺陷**：候选 id 来自别的租户，与本人 scope 求交后通常为空，
  患者域的"文档级收窄"实际长期失效。

**修复后**：租户/患者隔离子句提取为唯一实现
`backend.patient.retrieval.patient_scope_predicate()`，`patient_scope_filter()` 改为复用它；
`_candidate_document_ids()` 新增 `scope_predicate` 参数，患者分支必须传入该子句。
公开医学知识库是全局共享的，其查询**不应**带租户条件，这点由测试一并锁定。

**测试**：`test_patient_document_candidates_stay_inside_the_patient_scope`
（修复前实测收到的表达式为 `chunk_level in [1, 2] and (section_path like "%高血压%")`，断言失败）。

## 仍未修复

以下问题在审计中确认存在，本轮仍未改动：

- **前端 Markdown XSS**：`frontend/src/utils/markdown.ts` 未接 DOMPurify；
  登录态仍在 `localStorage`（`frontend/src/stores/auth.ts`）。
- **SSE 流式与会话拆除顺序**：`/chat/stream` 与审计中间件的 `finally` 拆除存在竞态。
- **已匹配路由上的未认证洪泛**：4.2 的进程内限流只覆盖 `/auth/*` 两个端点。
  以伪造 token 高频打 `/patient/*` 仍会按请求速率写入审计行（这是真实授权拒绝，
  不应丢弃）。这一项需要**在反向代理层**做限流，代码内不宜再收紧。
- **漏斗公开分支的 `query_all` 无上限**：`MilvusStore.query_all()` 分页累加**全部**命中行，
  而 `_candidate_document_ids()` 最终只保留 `FUNNEL_MAX_DOCUMENT_CANDIDATES`（默认 100）个
  不同文档——第 5 节修掉的是患者分支的越界，公开分支仍是全局集合上的无界读取。
  命中面很宽的主题词会让单次 `/chat` 请求把这批行全部读进内存。直接改成
  `limit=max_documents` 会显著改变收窄结果（同样 100 行可能只覆盖两三个文档），
  需先单独评估召回影响，故本轮未动。
- **同一患者范围内的跨用户文档操作**：`patient_documents.py` 的 `_scoped_record_query()`
  只校验 tenant/patient，不含 `owner_user_id`，而 `facts.py` / `fact_candidates.py` 的同名
  判定**包含**该条件。持有该患者 `write` 授权者可改写/删除其他用户上传的文档。
  两种读法（共享病历托管 vs. 上传者私有）代码目前无法同时成立，需要产品层面先明确；
  本轮未改。

修复上述项前，不应对外暴露该服务。
