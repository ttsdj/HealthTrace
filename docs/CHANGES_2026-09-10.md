## 1. JWT 签名密钥不再回退到公开常量（fail-closed）

**修复前**：`backend/infra/auth.py` 中

```python
SECRET_KEY = os.getenv("JWT_SECRET_KEY", "change-this-secret")
ALGORITHM = os.getenv("JWT_ALGORITHM", "HS256")
```

两处问题：

1. 未配置 `JWT_SECRET_KEY` 时使用硬编码的 `"change-this-secret"` 签名。
   该常量就在仓库里，任何人都能离线伪造任意用户（含 `admin`）的令牌。
2. `JWT_ALGORITHM` 可被环境变量覆盖。若被设为 `none`，
   `python-jose` 会接受无签名令牌——一条配置错误即可变成认证绕过。

**修复后**：

- 算法在代码中固定为 `HS256`，不再读取环境变量。
- 新增 `jwt_secret_key()`：每次调用实时解析密钥，缺失、长度不足 32 字符、
  或命中占位符特征（`replace` / `your-` / `change-this` / `example` / `placeholder`）
  时抛 `JWTConfigurationError`，**绝不回退**。
- 签发与校验路径统一把该异常转成 `503 authentication is not configured`；
  错误详情不回显具体原因，避免未认证调用者探测密钥配置状态。
- `STRICT_STARTUP=true`（`docker-compose.app.yml` 默认打开）时启动即校验，配置错误直接拒绝启动。
- `scripts/production_preflight.py` 复用同一份判定逻辑，不再各写一份。

**测试**：`test_signing_key_*`、`test_create_access_token_refuses_to_sign_without_a_key`、
`test_login_is_unavailable_when_the_signing_key_is_missing`、`test_signing_algorithm_is_pinned_to_hs256`。

**附带改动**：新增 `tests/conftest.py`，用 autouse fixture 为测试进程注入一把合法测试密钥。
否则 CI 在 `cp .env.example .env` 之前跑 pytest 会全部失败。

## 2. Milvus filter 表达式转义（堵住"单请求删库"）

**修复前**：`backend/api/resources.py`

```python
delete_expr = f'filename == "{filename}"'
```

Milvus filter 是**解析执行**而非参数化绑定。文件名由请求控制，
构造 `x" or filename != "` 即可闭合字符串字面量并追加条件，
得到的表达式等价于"匹配集合内所有行"——一次删除请求清空整个集合
（该删除路径同时清理 PostgreSQL 父分块与 Redis 缓存）。
同类插值还出现在 `patient_documents.py`、`patient/retrieval.py`、`rag/utils.py`、
`incremental_update.py`、`milvus_client.get_chunks_by_ids()`。

**修复后**：新增唯一实现 `backend.indexing.milvus_client.escape_filter_value()`，
先转义反斜杠再转义双引号；上述全部调用点改为经过它。
`incremental_update.py` 原有的 `_escape_filter_value` 改为转发，避免两份实现漂移。

**测试**：`test_public_document_delete_escapes_the_filename` 用桩 Milvus 捕获真实下发表达式，
断言注入串仍留在字面量内部（未转义引号恰好只有两个定界符）、且只有一个子句。

## 3. `clinician` 临床审核凭证不再可自助获取

**修复前**的完整提权链（已端到端复现）：

1. `POST /auth/register` 自助注册，`resolve_role()` 把非 admin 请求一律降为 `user`；
2. 调用任意患者域接口，`backend.patient.scope.ensure_user_scope()` 自动创建个人租户，
   并把该用户设为 `TenantMembership(role="owner")`；
3. `POST /tenant/members {"username": <自己>, "role": "clinician"}` ——
   `_tenant_admin_membership()` 只校验"是本租户 owner/admin"，通过；
   `TenantMemberCreate.role` 的允许集合是 `admin|clinician|viewer`；
4. 于是该用户获得 `TenantMembership(role="clinician", status="active")`；
5. `backend.evaluation.golden_review.reviewer_role()` 接受该成员身份作为临床审核角色，
   且**不限定租户**、对所有数据集生效；
6. `golden_readiness()["clinical_claim_allowed"]` 随之为真 ——
   任何人可为自己签发临床审核意见，golden 门禁形同虚设。

**修复后**：`clinician` 被认定为**平台级凭证而非租户内部职位**
（它是 `clinical_claim_allowed` 的来源），因此
`POST /tenant/members` 中分配 `clinician` **要求调用者为全局管理员**
（`backend/api/routes/access_control.py` 的 `_OPERATOR_ONLY_MEMBER_ROLES`）。

选择"限制分配方"而非"要求 `User.role == 'clinician'`"的原因：
后者与 `docs/SECURITY_AND_ACCESS.md` 记录的 `TenantMembership(owner/admin/clinician/member)`
模型冲突，且 `resolve_role()` 不会把任何请求映射为 `clinician`，
改后该凭证将无任何合法获取途径。

**测试**：`test_tenant_admin_cannot_mint_the_clinician_credential`
（修复前断言 `403` 实得 `200`，已实测确认）、
`test_platform_administrator_can_still_assign_the_clinician_role`（确认合法路径未被误伤）。

**连带调整**：`tests/test_access_security.py` 中原本用 `role="clinician"` 走通的成员流程
改为 `role="viewer"`——该用例验证的是"成员身份 + 患者授权"边界，与角色值无关。
